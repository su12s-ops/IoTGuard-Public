> 历史记录：保留当时的结果、失败与限制，不代表当前部署状态。当前入口见 [项目状态](../status.md)。

2026-10-25。当前修复后配置为 `glm-5.3-flash`、`openai` 协议、`https://open.bigmodel.cn/api/coding/paas/v4`，任务图版本 v5。原配置为 `anthropic` 协议、`https://open.bigmodel.cn/api/anthropic`。`DEEPSEEK_*` 是仓库沿用的配置变量名，不代表实际调用 DeepSeek；客户端名称代表协议，不代表实际返回模型。

原地址与[智谱 Claude API 兼容文档](https://docs.bigmodel.cn/cn/guide/develop/claude/introduction)一致。后续真实长输入对照仍复现了该链路的输出耗尽，因而切换到实测通过的原生路线。模型与密钥不变，没有自动切换到其他厂商或通用按量端点。

## 实际发现

| 问题 | 修复 |
|---|---|
| thinking 块从响应中被丢弃，工具下一轮无法保留原生协议内容 | 在内部消息保留完整内容块与签名，后续工具轮次原样回传；不作为报告、用户进度或解释输出 |
| 不合法的工具参数被替换为 `{}` | 明确拒绝，保留响应用量；不以空参数执行工具 |
| tool_result 块后追加文本会产生相邻的 user 轮次 | 合并为一个 user 内容块数组，保留工具结果在前、补充文本在后 |
| 只有思考而没有正文/工具的响应被当作普通空文本 | 明确标记 `model_response_no_actionable_content`；不接受为有效报告 |
| refusal / pause_turn 等结束状态缺少处理 | 作为不可用响应记录原因与实际 usage，不把未完成响应当最终报告 |
| OpenAI 兼容分支没有保留 GLM reasoning_content | 工具往返保留该协议字段；GLM 思考配置通过 extra_body 传输 |
| 有界流程对所有模型强制关闭思考 | GLM-5.3 系列改为已验证的 `thinking=enabled`、`reasoning_effort=low`；其他模型保持既有控制方式 |

[智谱深度思考文档](https://docs.bigmodel.cn/cn/guide/capabilities/thinking)当前说明 GLM-5.3/Flash 不支持禁用思考。但现场 Anthropic 兼容路由仍接受 disabled，且简单测试只返回工具/正文块。该差异已记录，不能断言 disabled 已在现场触发 HTTP 错误。新版按模型声明与实测可用组合选择参数。

第一阶段任务图版本升为 v4，修复协议块往返；第二阶段升为 `scoped-task-graph-v5`，更换经真实长输入验证的调用路线，避免复用旧协议/模型控制设置产生的角色报告。请求日志保存实际模型、stop_reason、输出上限、正文/思考字符数等统计，不记录密钥或思考正文。

## 第一阶段：短请求验证（不足以证明业务问题已解决）

使用现有账户和端点，工具仅返回本地测试整数，不连接设备，不执行设备命令。

1. disabled 对照：工具请求约 4.69 秒，最终答复约 4.31 秒；工具参数与结果正确；stop_reason 分别为 tool_use/end_turn，返回模型 glm-5.3-flash。
2. enabled/low：工具请求约 5.21 秒，最终答复约 4.83 秒；响应分别含 thinking+tool_use、thinking+text；完整原生块回传后正确生成结果。
3. 部署后应用级验证：真实 `UnifiedToolLoopAgent` 加现有 `build_llm_client()` 与 enabled/low 配置，约 9.98 秒成功；真实模型请求两次、测试工具执行一次、结构化结果正确。返回模型均为 glm-5.3-flash，stop_reason 为 tool_use/end_turn，真实用量 1149 token。不是使用 mock 模型的测试，也没有访问设备。

这些结果证明该小请求上的连通性和工具往返。它们不能证明复杂风险研判质量、全量性能或所有降级均由协议导致；此前 verified/mixed 字段矛盾属于报告语义问题，仍需单独验证。

离线回归覆盖签名内容块贯穿真实应用工具循环、混合 user 块合并、损坏参数拒绝、空响应与结束状态、真实用量保留、GLM OpenAI 字段传输及有界模型控制设置。

相关后端回归 52 项通过。部署期间基础镜像源 `docker.nju.edu.cn` 两次返回 403，最终基于本机刚成功构建的相同后端镜像补入最新应用文件；未修改依赖或镜像源配置。运行容器已确认 v4，健康检查为后端正常、节点在线、3/3 传感器健康。

## 第二阶段：真实故障复现与修复

历史运行 `UA-fd0dbc4002a0-14` 的漏洞、决策角色都记录了 `stop_reason=max_tokens`、输出 8192 token 后被拒收。这是明确的直接降级原因；同样材料上仅证明短工具成功并不能验证修复。

从该历史运行持久化状态重建决策材料与系统 Schema，初始输入约 26076 字符。原始请求全文未保存，因此这不是逐字重放原请求。诊断过程只读旧数据，不写正式裁定或执行设备操作。

第一组 Anthropic 对照在相同输入、相同 8192 输出上限下：

| 设置 | 耗时 | 结束状态 | 返回内容 |
|---|---:|---|---|
| 默认 thinking | 167.31 秒 | max_tokens | 只有 thinking，正文 0 字符，输出 8192 token |
| enabled / low | 161.50 秒 | max_tokens | 只有 thinking，正文 0 字符，输出 8192 token |

因此故障链为：长输入进入该兼容路由 → 推理持续占用输出额度 → 没有最终报告 → 接口结束为 max_tokens → 适配器正确拒绝不完整结果 → 角色降级。该路由在此请求上并未因 low 控制而收敛，不能声称 low 已经解决问题；未能观察服务端内部实现，不能断言是哪一层忽略了参数。

原生 Coding OpenAI 接口先通过账户可用性检查。重建的同一业务事实输入首次在约 42.11 秒返回完整正文，实际推理 287 token，总输出 2365 token；正文仍有两处计划枚举错误，记录为格式问题而不是协议截断。

随后在同一进程固定完全相同的初始逻辑 messages，SHA256=`c97f17ff9938b12ba368ee2bc4e39803e306df961fc64bc52576aa246d98ff60`，两条路线采用相同模型、相同 8192 输出上限：

| 路线 | 耗时 | 结果 |
|---|---:|---|
| Anthropic enabled/low | 171.35 秒 | 仍只有 thinking、正文 0、输出 8192，max_tokens 拒收 |
| Coding OpenAI enabled/low，应用工具循环与既有校验 | 67.81 秒 | succeeded，结构通过，引用与语义校验错误列表为空 |

初始逻辑输入相同；后者保留应用既有的一次格式纠错能力，未绕过 Schema 或事实校验。对照只支持这个复杂输入上的差异，不代表所有模型请求都有相同提速倍数。

已落实修复：

- 私有运行配置切换为 `openai` + `/api/coding/paas/v4`，保留模型和密钥；不自动退回旧路线。
- GLM 的 SDK 请求上限与既有 180 秒请求预算对齐，避免 OpenAI 客户端沿用 60 秒而提前打断。
- 对输出已耗尽等不可用响应，不再在相同输入/参数上盲目重试；保留首个 stop_reason 与实际用量。
- `ModelResponseError.details` 与请求日志保存正文/思考长度、块类型、输出上限；纯思考耗尽明确归类为 `reasoning_only_output_budget_exhausted`。界面与本地预算拦截分开显示。
- 新增回归验证该失败只调用一次模型、仍准确记录 17357 token 的实际总用量，并且日志不包含思考正文。

第二阶段相关回归 65 项通过，另有错误归类专项测试通过。部署基于本机缓存镜像补入应用与配置样例，依赖未变。
