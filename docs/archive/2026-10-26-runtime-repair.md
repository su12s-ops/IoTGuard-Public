# eBPF 与四智能体运行修复

> 历史记录：保留当时的结果、失败与限制，不代表当前部署状态。当前入口见 [项目状态](../status.md)。

2026-10-26，北京时间。针对当前 Docker 的 18080 控制台及其正式业务数据库。

## 已确认的问题与修改

1. 运行时状态接口每次完整读取 JSONL 历史再截尾。本轮改为从文件尾部分块读取，限制返回条数和读取字节数；返回取样范围、截断标志及读取字节数，取样数量不再冒充全量数量。
2. 健康检查和可靠性统计缺少时间索引。增加全局时间、资产/时间和传感器/时间索引，同时支持已有 SQLite 数据库的幂等升级。
3. 不同接口对传感器状态的解释不一致。健康、覆盖率和可靠性统一按心跳时效计算有效状态，另保留上报状态；近期成功的 logread 窗口为 reporting，过期的 running 不再显示在线。历史事件不能单独产生“健康”的建议。
4. Docker 返回的采集脚本路径错误。修正为镜像实际复制的 `/collector/run_falco_capture.sh`。
5. 模型排队时间提前消耗 HTTP 请求时限。排队仍受角色与整轮总时限限制；获得槽位后，HTTP 请求再按剩余总时限及原有请求上限计算，预算和并发上限未提高。
6. 共享报告等待每 50 ms 查库。增加完成通知与有界等待，保留期限核验；报告复用的实际等待时间单独记录，不再始终显示 0 ms。
7. 已终止的部分完成流程仍显示阶段 running。终态投影改为 partial/failed/interrupted，前端显示对应状态。
8. 风险列表会读取、解析并返回全部审计正文。现场历史正文累计约 915 MB，曾造成页面超时及高内存。列表现在读取审计元数据；列表页同时省略取证包和角色详细结果，详情查询仍保留既有入口。
9. 正式研判写审计时再次读取并复制设备全部历史证据，且把分析期间新到事件混入本次事实基准。新 `m5-facts-v3` 回执引用本次已经保存的证据快照、类别哈希及注册表摘要，原始材料保留在 `UnifiedAnalysisRun.state_json`。旧记录不改写；与旧事实结构比较时仍进入人审。无快照的兼容路径对完整证据流式计算内容摘要。
10. 构建证据快照时一次物化全部历史 ORM 对象。改为每批 256 行读取，保留完整的新鲜度、候选关联及历史摘要计算语义。

执行详情现在分别展示实际墙钟时间、各角色总时间、模型排队、模型等待、取证和共享报告等待。终态统计止于完成时间，并行角色时间不能相加当作整项耗时。

## 部署与实测

通过标准 Compose 构建并部署。部署前通过 SQLite 在线备份保存一致性副本，位于数据卷 `maintenance-backups/before-runtime-repair-20261026T001052Z.sqlite`；代码与静态文件备份保留在本地 `reports/runtime-repair-20261026/`。部署前检查没有运行中的正式研判。最终容器关键源文件 SHA-256 与工作区一致。

最终通过 18080 同源代理连续读取三次，耗时中位数为：

| 接口 | 中位耗时 |
|---|---:|
| `/api/health` | 0.0043 秒 |
| `/api/runtime/ebpf/status` | 0.2794 秒 |
| `/api/runtime/ebpf/reliability` | 0.0279 秒 |
| `/api/risk/ranking?include_details=false` | 0.2640 秒 |

本轮初始 Docker 运行时状态接口耗时 4.35 秒；风险页曾在 25 秒超时。上述数据来自当前 Docker，未与此前宿主机 8000 的旧库混算。

最终观测节点在线、三个传感器有效心跳均健康、运行时证据新鲜。运行时事件与统一安全证据均为 72,617 条，未归属传感器事件为 0，证据 outbox 待处理与重试均为 0。这些是观测时刻的结果；内核 drops 未提供时仍显示 unavailable。
