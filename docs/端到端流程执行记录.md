1. 事实载荷 `_candidate_facts` 只含事实输入：匹配事实（含内容型匹配指纹、版本、状态）、资产配置（暴露/业务等级、OS 版本、清单完整性、服务元组）、情报指纹、运行时**覆盖等级**（`runtime_status`：waiting/contextual/verified/not_observed——证据从无到有、从上下文到直接命中的跃迁仍是事实变化）；**删除** `asset_updated_at`、`runtime_event_ids`、`runtime_strength`。

3. 旧算法行（无载荷）一次性迁移：先按行上留存的事实字段（`affected_status`/`runtime_status`/`applicability_source`/`ubuntu_priority`）比对，仍一致则**保留结论**并记录 `candidate_facts_rebaseline` 治理事件（含新旧指纹与清单引用，盲窗如实留痕）；行上事实漂移仍按事实变化重置。

#### 6. 预算语义（57,156/55,000）澄清与验证

**规则**：角色 token 预算是**每次请求发起前的硬闸门**（`ensure_budget`/`reserve_request`：`role_usage >= limit` 即拒绝），不是请求后回滚；单个在途请求可以越过线，其**有效输出被接受**（完成请求可越线语义）；越限后该角色的所有后续请求（含再一次收敛请求）被硬闸拒绝。因此越限量**有界**——最多一个请求的用量，不会复利累加。该语义应表述为：边界处是软阈值（单请求可越线、有界超出），请求发起权是硬闸门；既不是严格硬上限，更不是无上限。

**实测印证**（运行 `UA-0268ce17f6ed-130` 审计记录，10-24 22:06 复验）：vulnerability_analyst 首次分析累计 37,466 后，投影判定下一轮工具请求会越限 → 改走**唯一一次**无工具收敛（发起时 37,466 < 55,000，过闸门）→ 收敛请求实际用量 19,690 → 合计 **57,156/55,000**（越限 2,156 ≈ 3.9%，单请求有界）；收敛输出经完整结构化校验 `status=succeeded`（不降低成功判定标准）；`role_budgets_exhausted=["vulnerability_analyst"]` 如实入库，该角色后续零请求。runtime_analyst 同语义（26,160/40,000，投影收敛 succeeded）。整运行 11 次请求全部可对账。

**收敛请求次数有界（代码结构保证，`agent_base.py`）**：工具循环内投影命中 → 调用一次 `_finalize_without_tools` 即返回（不再回到工具循环）；收敛内部 `_complete` 再过 `ensure_budget`/`reserve_request`（角色已越限则拒绝并显式降级、不发请求）；收敛后的结构化校验 `attempts=1`（无反馈重试）。外层重试即使触发，也会在循环顶部 `ensure_budget` 处对已越限角色立即降级。既有回归 `test_role_usage_projection.py` 6 项（投影收敛、额度充足不干预、已越限仍硬闸、重复调用压缩、结果变化全文返回、参数不同不压缩）本轮全量通过。
